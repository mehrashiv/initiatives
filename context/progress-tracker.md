- **User Management design decisions** (confirmed with the developer before documenting in `architecture.md`/`project-overview.md`):
  - **`requireEmailVerification` will be disabled project-wide**, not worked around per-user. The mockup's "Add user" sets a password directly (no email round-trip), and this project has zero SMTP configured — a normal `signUp()` call would leave a new admin-created user stuck unverified with no way to ever receive a verification email. Since this app has no public self-signup at all (every account, dashboard or in-app, is admin-vetted), the verification gate is redundant here, not a real security layer being removed. Confirmed empirically: both existing dashboard-created test accounts already have `email_verified = true`, consistent with this approach.
  - **"Add user" and "Remove user" use `createAdminClient({ apiKey: process.env.INSFORGE_API_KEY })`** (server-only secret, sourced from `.insforge/project.json`'s `api_key` field — never `NEXT_PUBLIC_*`), calling `POST /api/auth/users` (create) and the admin-only `DELETE /api/auth/users` (remove). These are InsForge **auth-system** endpoints, not `public`-schema tables — RLS/PostgREST never sees them, so there's no database policy that can enforce "only an app admin may call this." Both Server Actions must independently check the caller's own `profiles.role === 'admin'` before doing anything, which is a deliberate, documented exception to this project's "RLS is the only real enforcement" invariant (see `architecture.md`).
  - **Role is set once, at creation** — but *not* via `profile` metadata as originally planned here; see Feature 06's "Problems solved" entry below, this line was wrong. The end result is the same either way: no in-app control to change an *existing* user's role, so the SQL bootstrap path from Feature 04 (`run-raw-sql`, raw SQL bypasses RLS entirely via `project_admin`) remains the only way to fix a role after the fact.
  - **"Remove user" is blocked (not auto-reassigning) when the target still owns or created anything.** `initiatives`/`projects`/`tasks`/`activities` reference `profiles(id)` via plain FKs (no cascade) for `created_by`/`owner`/`who`; the Server Action checks for any such rows first and returns a clear "still owns N records — reassign first" error rather than attempting a delete that Postgres would reject anyway, or silently reassigning records to the removing admin (which would corrupt the `created_by` audit trail `architecture.md` calls permanent).
