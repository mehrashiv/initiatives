## Minor
### 🟡 Created task visibility check uses a stale `filters`, `components/tasks/tasks-view.tsx:295`
**Problem**: `handleCreateTask` calls `matchesFilters(newTask, filters, ...)` inside a promise `.then`. `filters` is the value captured when the handler started, not the value when the insert finishes.
**Why it matters**: If the user changes a filter while the insert is in flight (the modal closes on success, so the window is small), the toast can say "Task created" for a task that is now hidden, or the reverse. AC-13 would be wrong for that moment.
**Suggested fix**: Read the latest filters through a ref, or compute the toast from the current state at resolve time.

### 🟡 New task visibility ignores View As scope, `components/tasks/tasks-view.tsx:295`
**Problem**: The hidden toast checks only `matchesFilters`. The list is first narrowed by the View As scope (`scopedTasks`), so an admin viewing as a user who creates a task owned by someone else sees no task and gets plain "Task created".
**Why it matters**: The spec says the toast is about filters, so this is arguably per spec, but the user still cannot see the task and gets no explanation.
**Suggested fix**: Decide whether the toast should also cover scope; at least note the gap in the spec.

### 🟡 Toast timer is not cleared on unmount, `components/tasks/tasks-view.tsx:227`
**Problem**: `toastTimer` is cleared on the next toast but not when the component unmounts.
**Why it matters**: A pending timeout fires `setToast` after leaving the page. Harmless in React 19 but untidy, and the same pattern will leak in tests.
**Suggested fix**: Add a cleanup effect that clears the timer.

### 🟡 Unrelated Kanban width change, `components/tasks/kanban-board.tsx:37`
**Problem**: `max-w-85` on columns is not in spec 0001 and changes the layout for everyone.
**Why it matters**: It rides along with a state feature and is not covered by any acceptance criterion or test.
**Suggested fix**: Confirm it is intended and mention it in the spec or commit message, or split it out.

### 🟡 Restore validates against `projectOptions`, server validates against `projects`, `components/tasks/tasks-view.tsx:104`
**Problem**: The two id lists are built from different arrays. They match today, but nothing enforces it.
**Why it matters**: If `projectOptions` ever excludes some projects (for example archived ones), a URL with such a project would be kept by the server and a saved state would drop it, so the same value behaves differently by entry path (AC-8).
**Suggested fix**: Build both from one shared list, or add a short comment stating they must stay equal.
